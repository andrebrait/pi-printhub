# REST API

Date: 2026-10-31. Extends [the main design](2026-10-21-pi-printhub-design.md), [the settings page](2026-10-29-settings-page-design.md) and [notification channels](2026-10-30-notification-channels-design.md).

## 1. Goal

Other programs (Home Assistant, scripts, automations) use the same `/api` the web app uses: print a file, follow jobs, scan, read the printer's status and supplies, manage notification channels and silences, and change settings. They authenticate with an API token instead of a browser login. An API page documents every method, its parameters and its responses, and lets the owner try them.

## 2. API tokens

### 2.1 Storage

- `/var/lib/printhub/api-tokens.json`, mode 0600, written atomically like `settings.json`.
- Each token: `id` (server-assigned), `name` (1–60 characters), `access` (`read` or `full`), `created` and `last_used` (ISO 8601 UTC; `last_used` null until first use), and `hash`: the SHA-256 of the token in hex. The token itself is never stored.
- A token is `ph_` followed by 32 random bytes in URL-safe base64 (`secrets.token_urlsafe(32)`). The `ph_` prefix makes a leaked token recognisable.
- `last_used` is written at most once a minute per token, so a polling client does not rewrite the file every few seconds.

### 2.2 Using a token

- `Authorization: Bearer <token>` on any `/api/` request.
- The server hashes the presented token and compares it in constant time (`hmac.compare_digest`) with each stored hash.
- A request with a valid token skips the Origin check: that check stops other websites from using a logged-in browser's cookie, which does not apply to a token the client must present itself.
- A request with an `Authorization` header that is not a valid token gets 401 `{"error": "Invalid API token"}`, even if it also carries a valid session cookie. Failed token attempts count against the login rate limit per client address (429 after 5 a minute), so tokens cannot be guessed quickly.
- Without an `Authorization` header, today's behaviour applies: session cookie plus Origin check.
- Every HTTP path containing an ASCII control character (U+0000–U+001F or U+007F), including decoded `%0A`, is refused with 400 `{"error": "Invalid path"}` before authentication, Origin checks, share admission or body reads.

### 2.3 Access levels

| Access | Allowed |
|---|---|
| `read` | Every `GET` under `/api/`, except `GET /api/tokens`. Includes status, printer, jobs, documents and their exports and previews, notifications, settings (secrets are never returned anyway), channels, silences, defaults, recipients and scanner. |
| `full` | Everything `read` allows, plus every state-changing call (`POST`, `PUT`, `PATCH`, `DELETE`) except those in the next row. |
| Browser session only | `POST /api/login`, `POST /api/logout`, `POST /api/settings/password`, `POST /api/share/{token}/claim`, and everything under `/api/tokens`. A token gets 403 `{"error": "Not allowed with an API token"}`. |

A `read` token on a state-changing call gets 403 `{"error": "This API token is read-only"}`.

`POST /share` (the phone share target) and `POST /api/share/{token}/claim` are unchanged and not part of the token API.

### 2.4 Managing tokens

Browser session only.

| Method and path | Purpose |
|---|---|
| `GET /api/tokens` | `[{id, name, access, created, last_used}]` — never the token or its hash |
| `POST /api/tokens` | `{name, access}` → 201 `{id, name, access, created, token}`; the only time the token is returned |
| `DELETE /api/tokens/{id}` | Revoke; 204, 404 when unknown |

Creating and revoking a token add an `info`/`settings` event naming the token (never the token itself): "API token <name> created (read-only)", "API token <name> revoked".

Settings page: an **API tokens** card listing the tokens (name, access, created, last used, Revoke) and a form (name, Read-only or Full access, Create). After Create, the token is shown once in a read-only field with a Copy button and the note "Copy it now; it is not shown again."

## 3. OpenAPI

- `GET /api/openapi.json`: the OpenAPI 3.1 description generated by FastAPI. It needs the same authentication as the rest of `/api` (a session or any token). FastAPI's own `/docs` and `/redoc` stay off.
- Info: title "Print Hub API", the app version, and a short description of the two ways to authenticate.
- Security schemes: `bearerAuth` (HTTP bearer) and `sessionCookie` (API key in the session cookie). Every operation lists both, except the browser-only ones (session only).
- Every route has a summary, a one-line description, a tag (Status, Printing, Jobs, Documents, Scanning, Notifications, Settings, API tokens) and declared request and response models, so the schema shows real fields. Error responses are documented as `{"error": string}` with their status codes.
- Uploads (`POST /api/uploads`) are documented as `multipart/form-data` with a `file` field; exports and previews as binary responses with their media types.
- Tests pin the contract that matters to clients: every `/api` route appears in the document, has a tag and a response model, and the browser-only routes list only `sessionCookie`.

## 4. API page

- `/api.html`: Swagger UI from `swagger-ui-dist` 5.34.1 (Apache-2.0), vendored unmodified under `static/vendor/swagger-ui/` (`swagger-ui.css`, `swagger-ui-bundle.js`, `LICENSE`, plus `NOTICE` if present), integrity-checked against the npm tarball and recorded in `static/vendor/LICENSES.md`.
- The page has the app's header and footer and loads `/api/openapi.json`. Our own small script starts Swagger UI; there is no inline script.
- "Try it out" works with the browser's session (same origin, cookie and Origin sent by the browser) and with a token entered under Authorize.
- Swagger UI's own theme is light; in the dark theme the page keeps a light panel for the documentation rather than restyling Swagger UI.
- Linked from the footer ("API") and from the API tokens card.
- The service worker does not precache the Swagger UI files (about 1.5 MB); they are fetched when the page is opened.

## 6. Testing

- Python:
  - Tokens: creation returns the token once, only the hash is stored (0600), revocation, `last_used` throttling.
  - Auth: a valid token passes without an Origin header; an invalid or revoked token gives 401 even with a session cookie; failed attempts are rate-limited; a `read` token is refused every state-changing route and allowed every GET; browser-only routes refuse any token; session behaviour unchanged.
  - Every `/api` route is classified (a test fails when a new route is added without a decision on token access).
  - OpenAPI: served with auth, refused without; every route tagged, typed and documented; security per route as in section 3.
  - Events for token create and revoke never contain the token.
- JS: the API tokens card lists, creates (token shown once, Copy), and revokes; the API page script starts Swagger UI with `/api/openapi.json`.
- On the Pi: create a read-only and a full token; `curl` the status with each; print a file with the full token; the read-only token is refused on print; the API page lists the methods and Try it out works.

## 7. Out of scope

- Token expiry dates (revocation covers it).
- Per-area scopes beyond read and full.
- API versioning (`/api/v1`): the API keeps today's paths.
